My market-data repo has 32 collection scripts. Fourteen of them drive a real web browser, because the data they want only appears after a page has run its JavaScript. Twelve use Playwright and two use Selenium, and the two Selenium ones are the oldest files in the folder.

That ratio is the honest summary of my opinion, but it is not an argument, and the reasons people usually give for it are mostly wrong. This is what actually changed when the same jobs moved across, including the part where the tidy story about Playwright does not survive contact with my own code.

What these tools do, in one paragraph

A lot of a modern web page does not exist in the file the server sends you. The server sends a mostly empty shell plus JavaScript, and the numbers you can see in the browser get filled in a moment later. If you fetch that page the plain way — the equivalent of curl — you get the shell. So instead you start an actual browser, invisibly, and tell it what to do: open this page, click that button, now give me the text. Selenium and Playwright are both ways to give a browser those instructions from code. Selenium arrived in 2004 and is the reason the whole category exists; Playwright is Microsoft's, from 2020.

Both work. Anything one can scrape, the other can scrape. The differences are in how much code you write around the parts where a page is slower than your script.

The difference that shows up on line one: waiting

The core problem in browser automation is that your code runs instantly and a page does not. You ask for a button that has not been drawn yet, and you get an error rather than a button.

Selenium's answer is that you say so explicitly. You wrap the thing you want in a wait that polls until a condition holds:

self.wait = WebDriverWait(self.driver, 15)
news_tab = WebDriverWait(self.driver, 10).until(
    EC.element_to_be_clickable((By.XPATH, "//a[contains(text(),'News')]")))

That is from my Economic Times news scraper, which is one of the two Selenium files. It is 563 lines, and 12 of them are except clauses. One catches StaleElementReferenceException, which is worth explaining because it is the single most Selenium-shaped thing in the codebase: when you find an element, Selenium hands you a reference to that specific object in the page. If the page redraws that part of itself — which single-page sites do constantly, for reasons that have nothing to do with you — your reference now points at something that no longer exists, and using it raises. The element is still there on screen. Your handle to it is not.

Playwright does not hand you the element. It hands you a locator, which is a stored description of how to find the element, resolved fresh every time you use it, with a wait built in:

await page.locator("input[name='password']").fill(PASSWORD)
await page.get_by_role("button", name="Log in").click()
await page.wait_for_url("**/home", timeout=15000)

Each of those three lines waits on its own for the element to exist, be visible, and be ready to be interacted with. There is no wait object, and a redraw between two lines is not an error, because the description is re-run rather than a handle being reused. That is the real difference, and it is a difference in what you have to think about rather than in what is possible.

Where that story breaks: my Playwright scripts are full of fixed sleeps

The usual claim is that auto-waiting means you stop writing sleep(5). I counted mine. Across the 12 Playwright scripts there are 52 calls to wait_for_timeout, which is a fixed sleep wearing a different name, against 25 uses of the proper "wait until this appears" call.

Those 52 are not all the same thing, and separating them is the useful part:

Pacing. A good share of them are deliberate — a pause between requests so a script reads more like a person and less like a flood. That has nothing to do with which tool is in use, and removing it would be a mistake.

No signal to wait on. Auto-waiting answers "is this element ready", which requires you to know which element proves the page is done. When clicking a filter triggers a background fetch that swaps numbers inside table cells that were already on the screen, there is no new element to wait for, and the honest options are to wait for the network response by URL or to sleep. I reached for the sleep in more places than I would defend.

So the accurate version of the claim is narrower than the popular one: auto-waiting removes the class of failure where the element was not there yet. It does not remove the need to know when a page has finished, and it does not write that knowledge for you.

Logging in once instead of every run

This is the feature that actually changed how I structure scripts, and it gets less attention than the waiting.

Several sources only show data to a signed-in account. Signing in from code is the fragile part of any scraper: it is the most heavily defended page on the site, and it is where a wrong move costs you the account rather than the run. Playwright lets you do it once, by hand, in a visible browser, and then save everything the browser learned — cookies and stored site data — to a JSON file:

browser = await p.chromium.launch(headless=False)   # visible: log in as a human
context = await browser.new_context()
# ... fill the login form once, then:
await context.storage_state(path="storageState.json")

Every later run starts from that file and is already signed in, with no credentials in the scraping code at all. The equivalent in Selenium is to point Chrome at a saved user profile directory, which does work and is heavier: it is a whole browser profile on disk rather than a small file, it carries state you did not ask for, and two runs cannot share it at the same time. Being able to commit a script that has no password in it, and hand the session file separately, is a structural improvement rather than a convenience.

One process, many pages

Playwright's Python API has an async version, so a single script can drive several pages at once inside one process. The Selenium way to get concurrency is a browser per thread, which is much heavier and is the reason a large Selenium setup ends up wanting a Grid — a separate service that hands out browsers. If you would rather not write the pool yourself, Crawlee wraps Playwright with request queueing, retries and concurrency limits already built; I use it in product-explorer for exactly that reason.

One caution from my own logs: concurrency is where scraping bugs come from. Three of the bugs in my year of ingestion bugs were caused by parallel workers, not by the sites. Running eight pages at once also means arriving at a site eight times as fast, which is the fastest way to turn a working scraper into a blocked one.

The operational difference nobody mentions until it breaks

Selenium drives a browser you supply. That means the browser and the driver that talks to it have to be version-compatible, and Chrome updates itself roughly monthly. The usual patch is webdriver-manager, which downloads a matching driver at runtime — it is in my requirements file for exactly this reason. It works, and it adds a network call at startup to a place where you did not previously have one.

Since 4.6, Selenium ships Selenium Manager, which does the same job in-process and makes webdriver-manager largely unnecessary — worth knowing if you last touched Selenium before that, because it removes most of the version-matching pain this paragraph describes.

Playwright downloads and pins its own browser builds through playwright install. The browser is a dependency of the project rather than a property of the machine, so a script that ran last month runs the same way this month, and the same way in a container. For unattended jobs on a schedule, that is worth more than any API difference.

Where the choice makes no difference at all

Neither tool helps with the thing that actually stops scrapers, which is being refused. My clearest example: Trendlyne, a stock-data site I use to fill gaps, started returning 405 to a plain Python request. It was not looking at the code, the headers, or the user agent. It was looking at the shape of the TLS handshake — the pattern of the encrypted connection itself, which differs between Python's networking library and a real Chrome. No amount of browser automation choice changes that; what fixed it was curl_cffi, which makes a plain HTTP request whose handshake matches Chrome's, and no browser at all:

# curl_cffi impersonates a real browser's TLS/JA3 fingerprint, which is what
# gets past Trendlyne's Cloudflare bot mitigation (plain `requests` gets 405'd).
from curl_cffi import requests as cffi_requests

That is the general shape of it. A browser is the answer when the data genuinely does not exist until JavaScript runs, and it is the most expensive tool available for everything else — a Chrome instance to fetch a JSON endpoint costs hundreds of megabytes of memory and a second of startup to do what one HTTP request does in 200 milliseconds. Of my 32 scripts, 18 never open a browser. One of those 18 is still called trendlyne_selenium.py and contains no Selenium at all — it drives nothing, fetches HTML directly, and the filename is left over from the version that needed a browser to get the same rows. Why scrapers get blocked goes through the rest of that stack.

How I would choose now

New scraping work: Playwright. Locators remove a class of error, sessions save to a file, browsers are pinned, and concurrency does not need a second service.

An existing Selenium suite: leave it. Both my Selenium scripts still run. Nothing above is worth a rewrite on its own, and a working scraper is worth more than a modern one. I ported nothing; I only wrote new work in the new tool.

Cross-browser testing across a fleet, or a team already running Grid: Selenium is a W3C standard with two decades of infrastructure behind it, and that matters more for a test suite that must run on browsers you do not control than it does for a scraper you run yourself.

Neither, if the page is not the point. Open the network tab, find the endpoint the page is calling, and call that instead. It is faster, it breaks less often, and it is a smaller thing to be blocked for.

One limitation on all of the above: this comes from porting the same jobs between tools over about two years, not from a controlled benchmark. I did not run both against the same site on the same day with a stopwatch, so nothing here should be read as a speed claim. The parts I would defend are the ones about failure modes and operations, because those I have logs for.

References and further reading

Playwright's own page on actionability lists exactly which conditions each action waits for, which is the most useful page in either project's documentation and is the thing to read before deciding whether auto-waiting covers your case.

Selenium's waits documentation is direct about why implicit waits and explicit waits should not be mixed, which is a footgun I hit before I read it.

Documentation worth having open

  • Playwright — authentication: the save-the-session-to-a-file pattern from above, with more care about when a saved state expires.
  • Playwright — trace viewer: records a run and replays it with the DOM, network and console at every step. It is the single biggest debugging difference between the two tools and I did not use it for far too long.
  • Playwright — request interception: block images and fonts, or answer a request from your own data. Blocking media alone typically halves page-load time on a scrape.
  • Selenium Manager: the built-in driver resolution that replaced third-party driver managers from Selenium 4.6 onward.
  • Selenium BiDi: the bidirectional protocol that closes most of the capability gap — network interception and console access from Selenium, standardised rather than Chrome-only.
  • W3C WebDriver and the Chrome DevTools Protocol: the two wire protocols underneath all of this. Reading the second explains why Playwright can do things the first cannot express.

Tools mentioned

  • Crawlee for Python — queueing, retries, proxy rotation and concurrency around Playwright, so you are not rebuilding a crawler each time.
  • curl_cffi — HTTP requests whose TLS handshake matches a real browser, which is the fix when the page itself was never the problem.
  • undetected-chromedriver — the Selenium-side answer to automation detection, if you are staying on Selenium.
  • Scrapy — still the right tool when no JavaScript is involved: it is faster than any browser and its AutoThrottle handles pacing for you.
