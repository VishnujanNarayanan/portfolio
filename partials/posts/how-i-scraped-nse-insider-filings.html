Plenty of public archives paginate by date: give me a start date and an end date, and I will give you what falls between them. Twenty years of history then means a few hundred requests, a way to remember where you stopped, and a way to notice when an answer was incomplete. This is that job, done against one real source.

When a company director buys or sells shares in their own company, they have to tell the exchange. In India those disclosures are public, and the National Stock Exchange serves them from what it calls its PIT endpoint — PIT being Prohibition of Insider Trading, the regulation that requires the disclosure in the first place. I wanted all of them, going back twenty years, in one file I could keep up to date.

The endpoint will absolutely give you insider filings. What it will not do is tell you when it has given you fewer than you asked for. That single property shaped every design decision below, and it is the reason this took three attempts to get right.

Why an endpoint that paginates by date forces windowing

The obvious first attempt is one request covering 2005 to today. It fails, but it fails in three different ways depending on how wide the range is, and only one of them is obvious.

A very wide range times out — loud, easy to notice, easy to handle. A merely wide range does something worse: it returns quickly, with a valid response, containing some of the data. There is no error, no flag, no count telling you what the total should have been. If you are not comparing the result against something external, a truncated response and a complete one look the same.

So the fix is not "retry harder", it is to never ask a question big enough to get truncated. I split the whole history into fixed windows and walk them one at a time:

DEFAULT_CHUNK_DAYS = 180   # max span fetched per request when looping a wide range

def fetch_range(session, from_date, to_date, chunk_days, retries=3):
    """Fetch a wide date range by splitting it into chunk_days-sized windows."""
    start = from_date
    while start <= to_date:
        end = min(start + timedelta(days=chunk_days - 1), to_date)
        ...
        start = end + timedelta(days=1)

180 days is not a documented limit. I found it by requesting progressively wider windows and watching where results started going missing, then backing off. That is the only way to find a cap nobody publishes: deliberately walk into it while you can still tell you have hit it. At 180 days, twenty years is about forty requests rather than thousands.

This also decides how updates work. The first run pulls the full twenty years. Every run after that starts from the newest filing already stored — but backs up a buffer of days first, rather than resuming exactly where it stopped. That buffer exists because filings arrive late: a trade from last Tuesday might be disclosed next Monday. Resume exactly where you stopped and you will step straight over it, permanently, because you will never ask about that date again.

Overlapping windows mean deduplication has to be right

That buffer is deliberate re-reading. Every update re-downloads filings I already have, which means the pipeline needs a reliable way to recognise a record it has seen before. That check is not a safety net here — it runs on every single update, and if it is wrong the damage is immediate.

Mine named columns that do not exist, and it stayed that way for a while because the failure has no symptom. Deduplication works by building a key out of a few fields that together identify a record, then discarding rows whose key you already hold. I wrote my key from memory instead of from an actual response:

# What I used. None of these are real NSE column names.
DEDUP_KEYS = ['personName', 'acqQty', 'securityName']

# What the endpoint actually returns.
DEDUP_KEYS = ['symbol', 'intimDt', 'acqName', 'secAcq']

Because none of those first three columns existed, every row produced the same empty key. To the deduplicator, every filing for a company on a given day looked like the same filing repeated — so it kept one and dropped the rest. A company that disclosed four separate transactions in a day was stored as one. Nothing raised an error, because asking pandas for a column that is missing while building a key is not, by itself, a crash. The row count still looked plausible, because it was never compared to anything.

Fixing the key exposed a second bug hiding underneath it. I had implemented the dedup as a merge — joining new rows against stored rows to see which already existed. A merge against data that already contains duplicate keys does not remove duplicates; it multiplies them, because each new row matches several stored rows and you get one output row per match. So the pipeline went from silently deleting filings to silently inventing them.

The replacement is a set-membership test, which people call an anti-join: build the set of keys already stored, and keep only the new rows whose key is not in it.

def deduplicate(new_df, existing_df):
    new_keys = _composite_key(new_df, DEDUP_KEYS)
    existing_keys = set(_composite_key(existing_df, DEDUP_KEYS))
    return new_df[(~new_keys.isin(existing_keys)).values]

Unlike the merge, this cannot inflate anything, because it never joins — it only asks yes or no about each incoming row, so duplicates already sitting in the stored data cannot multiply the result. If you would rather keep using DataFrame.merge, passing validate="one_to_one" makes it raise on exactly the inflation case instead of performing it quietly.

The same record does not arrive the same way twice

A key only identifies a record if the same record always produces the same key, and in practice it does not. The same quantity comes back as 629221 from one place and 629221.0 from another. The same date is 15-Jan-2026 here and 2026-01-15 there. Compared as raw text those are different values, so the same filing gets a different key each time and is stored twice.

So before the key is built, every field is forced into one canonical form — dates to a single format, anything numeric to a number:

for k in dedup_keys:
    if k == 'intimDt':
        col = pd.to_datetime(df[k], errors='coerce').dt.strftime('%Y-%m-%d')
    else:
        # '100', 100 and 100.0 all collapse to one key;
        # names are not numeric, so they fall back to their text form.
        numeric = pd.to_numeric(df[k], errors='coerce').astype('float64')
        col = numeric.where(numeric.notna(), df[k]).astype(str)
    parts.append(col.fillna('').astype(str))
return parts[0].str.cat(parts[1:], sep='|')

This looks like housekeeping and is not. It is what makes the next problem solvable at all.

NSE is a month or two behind itself

Collecting the history turned out to be the easy half. The harder problem is that a filing takes roughly 30 to 60 days to appear in NSE's searchable history after it is disclosed. For a twenty-year backfill that does not matter. For anything current it means the most recent two months of the dataset were always incomplete — and, again, nothing in the response says so. The data looks finished because there is no marker for "still arriving".

The only fix is a second source that publishes sooner, so the pipeline supplements the last 60 days from one, maps it onto NSE's column layout, and merges it against what NSE has already given. That merge is only safe because of the normalisation above. Without it, the same filing from two sources produces two different keys. You end up with a dataset duplicated everywhere the sources overlap, which is worse than having one source.

That second source did not want to be read, in two specific ways worth knowing about because neither is obvious.

First, it started returning HTTP 405 errors through Cloudflare. Rotating the browser identity in the request headers changed nothing. The block was not reading the headers. It was fingerprinting the TLS handshake — the way the encrypted connection itself is opened, which differs between a Python HTTP library and a real browser no matter what the headers claim. curl_cffi opens the connection the way Chrome does, which gets past it; the full stack of blocking layers is in why your scraper gets blocked. But the more expensive part of that failure was the reporting: a fully blocked run finished successfully with zero new rows, which is exactly what a genuinely quiet day looks like. It now prints an explicit pass or fail summary, so "blocked" and "nothing new" can never again look identical.

Second, the free tier caps a response at 200 records per window and does not mention it. Ask for a month over a busy period and you get 200 records and no truncation flag anywhere in the response — the same silent shortfall as NSE's, from a completely different system. The supplement now fetches one day at a time, because a single day almost never exceeds 200 filings. Also, one IP address will not survive a full historical crawl of that source, so it runs through a rotating pool of proxies.

What I would do differently

Every failure in this post has the same shape: the output was plausible, and nothing checked it. Three things follow from that.

Check the totals against something outside the pipeline. Counting filings for a handful of companies I could verify by hand, and comparing against the exchange's own published figures, would have caught the dedup-key bug in a day instead of months. No amount of internal consistency would have, because the pipeline was perfectly consistent with itself.

Treat "nothing new" as a claim that needs evidence. It is the correct answer often enough to be unremarkable and wrong often enough to be dangerous — it was the visible symptom of both the Cloudflare block and the 200-row cap. Anything that can legitimately return nothing has to be able to say whether it looked and found nothing, or never got to look.

Decide what happens when a filing is corrected. If a company amends a past disclosure, the key sees a record it already holds and drops the correction. That was never a decision; it is a side effect of using set membership, and for a compliance-adjacent dataset it is the gap that bothers me most.

References and further reading

SEBI's Prohibition of Insider Trading Regulations, 2015 (the original gazette notification, amended several times since) set out who has to disclose what and by when. Those deadlines are the reason the data arrives late rather than wrong, and reading them is what turned "the source is unreliable" into a schedule I could design around.

NSE's insider trading disclosures page shows the same records a human would see. It is the fastest way to check a single company by hand when you suspect your own pipeline is dropping rows — and doing that check is what surfaced the deduplication bug.

The techniques, generalised

  • Airflow DAG runs and backfills — the standard vocabulary for "process this window, then that one, and let a rerun repair a window that failed". Worth reading even if you never install it, because it names what a hand-rolled windowed backfill is doing.
  • dbt snapshots — the standard answer to a source that revises history, which is what a filing amended after publication is.
  • pandas merge — validate="one_to_one" raises on the join that turns deduplication into duplication.

  • Python robotparser and RFC 9309 — what a crawler is expected to respect, in three lines of code and one short standard.
