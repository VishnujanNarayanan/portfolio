The deciding number was not speed and it was not price. It was 45.

My job-search bot makes exactly one call to a language model per job advertisement it finds: read the ad, return the title, the seniority, the years required, the pay range and the skills, as structured fields rather than prose. The hosted free tier I was using allows 1,000 requests and 100,000 tokens a day. At roughly 2,200 tokens per advertisement, the token budget runs out first, at about 45 advertisements a day. A single run reads 25. Two runs and the day is over.

So the parse moved onto a laptop GPU — a 6GB RTX 4050 — with the hosted providers kept as fallbacks. This is what that actually cost and bought, including one measurement I reported as a success before it had measured the thing I cared about.

What "running a model locally" means, and what limits it

A language model is a large file of numbers. To answer quickly, that file has to sit in the memory attached to the graphics card — VRAM — because that is the memory the chip doing the arithmetic can reach at speed. Anything that does not fit spills into ordinary system memory, and the answer arrives at a small fraction of the pace.

So the model you can run is decided almost entirely by one number: how much VRAM the card has. Mine has 6GB. Roughly what that buys, at the usual four-bit compression — quantisation, which stores each weight in four bits instead of sixteen and costs a little accuracy for about a quarter of the size:

  • 3–4 billion parameters — about 2.5GB. Comfortable, fastest.
  • 7–8 billion — about 4.7GB. The largest that makes sense here, and what I run.
  • 13–14 billion — about 9GB. Spills, and slows accordingly.
  • 26 billion and up — about 17GB. Not viable on this card.

I got this wrong in a way worth naming, because the mistake is easy to make: I first sized the model against the 7.6GB of system memory my Linux environment reported, which is a figure about the host's RAM split and has nothing to do with what the GPU can hold. Raising it would not have allowed a larger model. VRAM caps model size; system RAM only matters for the layers that spill. A partially downloaded 26-billion-parameter model, 17GB of it, was sitting on the disk from before I understood that. It was deleted rather than resumed. If you want to check a model before downloading it, the file sizes on any Ollama model page are the number to compare against your VRAM, not the parameter count.

Even at 7 billion the fit is not clean. During a real run the server reports 5.1GB resident and an 18/82 split between CPU and GPU — a fifth of the work lands on the processor because the model plus its context window does not quite fit. That is the honest cost of 6GB, and it shows up in every latency figure below.

The comparison, on the same task

Both sides ran the same schema against the same job advertisements:

  • Hosted, 70-billion-parameter model: 1.6 seconds per advertisement.
  • Local, 7-billion-parameter model: about 6 seconds, plus 18 seconds the first time while the model loads into VRAM.

Roughly four times slower. For a 25-job run that is two and a half minutes against forty seconds, on a pipeline that runs a few times a day and that nobody is waiting on. That is the trade in one line: four times the latency, in exchange for the cap disappearing entirely.

The cap is not the only thing that goes. With no token budget, advertisements no longer have to be clipped to fit — and mine average 4,400 characters, reach nearly 12,000, and mention pay a median of 77% of the way in. Clipping to survive a hosted budget was measurably discarding the part of the text I most wanted. Nothing leaves the machine either, which matters more for a personal document than for a job ad.

What I will not claim is a cost saving. The GPU is a laptop I already own, the electricity is not metered separately, and the hosted tier I was hitting is free. If you are choosing between a rented GPU and an API, that is a real calculation and this is not it — the case here is caps and privacy, not money.

Getting a small model to return valid structure

A 7-billion model is not a 70-billion model, and the difference shows up first as malformed answers rather than as wrong ones. Mine kept failing validation in one specific way: asked for the employment type, it answered hybrid, which is an answer about location:

1 validation error for JDParsed
job_type
  Input should be 'fulltime', 'contract', 'internship' or 'parttime'
  [type=literal_error, input_value='hybrid']

The usual handling is to notice after the fact and ask again. Each re-ask is a whole new inference, so one call took 83 seconds across four attempts.

Two fixes, and the difference between them is the useful part.

Describing the fields better. The two fields were described as "Employment type if stated" and "Work arrangement if stated", which are genuinely easy to conflate. Rewriting each description to explicitly exclude the other took it from four re-asks to zero or one. Cheap, and it helps every model. It is still persuasion.

Making the wrong answer unproducible. A model generates one token at a time, choosing from everything it could say next. Constrained decoding narrows that choice to what the schema permits — after "job_type": ", the only continuations available are the four allowed values. hybrid is not rejected after the fact; it is never available. Ollama compiles a JSON schema into that constraint directly; the same idea underlies llama.cpp's grammars and OpenAI's structured outputs, so the technique transfers whichever side you end up on.

With the schema enforced, five responses out of five validated with no re-asks, and the average call came down to about six seconds. I wrote that up as faster and correct, because the re-asks were the latency.

Where that conclusion was too strong

"Five out of five valid" measures conformance to a schema. It does not measure whether the answers contain anything.

Three of the fields — the required skills, the nice-to-haves, the responsibilities — were optional lists. An absent key is valid. So a response that named not one skill from the advertisement scored exactly as well as a complete one, and my check could not tell them apart. Measured across real advertisements rather than the one test case: the local model returned no required skills at all on 71% of them, while the hosted model populated them. The scoring downstream depends on those skills, so the parses were passing validation and feeding an empty comparison.

Separating the causes took an ablation — twelve advertisements, two runs each, changing one thing at a time:

  • The schema permitted it. The three list fields had defaults, so they were not in the schema's required set, and the grammar allowed the model to skip the keys entirely. The keys were absent, not empty — the empty lists visible downstream were manufactured by my own model definition after the fact.
  • The system prompt licensed it — "when a field is not stated, return null or an empty list".
  • The user prompt never asked for them. Every scalar field had an explicit instruction. These three had none.

Fixing only the prompt moved the empty rate from 71% to 62% while sharply improving the quality of whatever did come back. That split is the finding worth carrying: the schema controls whether a field appears at all; the prompt controls how good it is. Both were needed. Routing the local model through the same schema-stating path the hosted providers use, plus a prompt that names the three fields and asks for exhaustive extraction, took it to 0 empty out of 12.

There is one more thing in this sequence I would flag to anyone building the same pipeline. An early measurement concluded that the local server's OpenAI-compatible endpoint ignored schema enforcement, so I wrote a separate transport that spoke to its native endpoint instead. Re-measured later against a current version with a direct probe, that endpoint does honour it, respecting both required fields and minimum list lengths. The original measurement was either confounded or accurate for a version that has since moved. The measurement itself is not the interesting part — measurements go stale. What made it consequential is the chain it started: the conclusion was written into a code comment, the comment justified keeping a second transport, and that second transport is where the missing-fields behaviour lived. The bespoke transport has been deleted. Measurements about someone else's software have a shelf life, and a comment asserting one should carry the date and the version it was taken against.

How I would choose

Hosted API when the task is hard, latency is user-facing, or volume is spiky and unpredictable. A 70-billion model on someone else's hardware is better at reasoning than anything that fits in 6GB, and no amount of prompt work closes that.

Local when the task is narrow and repetitive — extract these fields from this document — when the volume is steady and would collide with a daily cap, when nobody is waiting on the response, or when the text should not leave the machine.

Both, ordered by cost. What I actually run is a chain: local first because it is uncapped, then the free hosted tier, then a metered account that is only reached when everything free has failed. The whole chain is in Job_Application_Bot if you want the wiring. That also means the classification described in what a 429 really means has to be right, since it decides when to give up on one link and move to the next.

If you take one thing: constrain the output with a schema, then measure whether the fields have content, not whether they parse. Those are different tests and only the second one is about the model.
