These two messages arrived from the same API, six hours apart, both as HTTP 429:

429 Rate limit reached ... on tokens per minute (TPM):
    Limit 12000, Used 10986. Please try again in 3.035s.

429 Your project has exceeded its monthly spending cap.

The first clears in three seconds. The second holds until somebody raises a limit or the month rolls over. Any retry loop that treats them the same handles one of them badly, and which one depends on which way you guessed. Sorting this out properly took three rounds, and the code that came out of it is about forty lines.

What a retry loop is, and the assumption inside it

Programs that call other people's services fail intermittently: a connection drops, a server is briefly busy. The standard response is to try again after a pause, doubling the pause each time — 2 seconds, then 4, then 8, then give up. That is exponential backoff, and it is close to free to write — or to get for nothing from tenacity in Python, or urllib3's Retry if you are already using requests:

except Exception as exc:
    if attempt < attempts:
        time.sleep(delay)
        delay = min(delay * 2, max_delay)

Written that way, the loop encodes a belief: that every failure is worth waiting for. My batches ran 25 items at a time, five attempts each, with the pause capped at 90 seconds. When the provider retired a model and every single call began returning 404 no longer available, that belief turned a permanent failure into roughly four minutes of waiting per item, applied to all 25. The run did not crash. It produced identical errors for fifteen minutes and then finished.

So the taxonomy needs at least two classes, which is the version most retry code eventually gets to:

  • Transient — 503, timeouts, 429. Retry with backoff.
  • Permanent — 404 unknown model, 401 bad key, 400 malformed request. Fail immediately; the next attempt is identical to this one.

I wrote that, and left a comment saying 429 was deliberately absent from the permanent list, because rate limiting is transient by definition and must keep retrying. The spend-cap message above arrived a few hours later and showed the gap.

The third class is about scope, not recoverability

A spend cap is not recoverable inside a run, but that is not the interesting part. The interesting part is that it says something about every subsequent call, not just this one. A 404 on item 3 tells you nothing about item 4. A spend cap on item 3 tells you exactly what will happen to items 4 through 25.

That is a third class, and the property that defines it is scope:

  • Transient — scope: this call. Retry.
  • Permanent — scope: this call. Fail this item, continue the batch.
  • Exhausted — scope: the whole account. Stop the batch, or move to a different provider.

The reason this class gets missed is built into HTTP: a status code says what went wrong and never says how widely. Both a per-minute throttle and a monthly spend cap are refusals to serve you right now, so both are 429, and the difference between them lives only in the human-readable text.

Which means you have to read the text. That sounds unappealing and it is unavoidable — and it also created the next problem.

A few providers do better than prose. Where a RateLimit header is present it tells you the limit, what is left and when the window resets, as structured fields you can act on without pattern-matching English. It is still a draft standard, so treat it as a bonus rather than a plan.

Classifying on message text, and the phrase that broke it

Two practical notes before the failure, because both surprised me.

You cannot classify by exception type. Between the SDK, the structured-output wrapper and the transport, one failure arrives as three nested classes wrapping each other. The status text is the one thing that survives every layer.

Vendors write error messages for humans. That is the trap. My list of "this account is exhausted" markers included the substring billing, which is reasonable — spend-cap messages mention billing. But this provider appends an upsell to every rate-limit message it sends:

429 Rate limit reached for model `llama-3.3-70b-versatile` on tokens per minute
(TPM): Limit 12000, Used 10986, Requested 1621. Please try again in 3.035s.
Need more tokens? Upgrade to Dev Tier today at https://console.groq.com/settings/billing

Routine throttling, clearing in three seconds, containing the word that meant "your account is finished". The classifier promoted it to exhaustion and the run moved to a fallback provider that was itself spend-capped. Two runs ended early that way, at 5 of 21 jobs and 4 of 13.

The taxonomy was not wrong. The evidence used to detect one of its classes was contaminated by text that had nothing to do with the class — an advertisement, not a description of the error. The fix is to make classification ordered, so a narrow, specific signal outranks a broad, incidental one:

def _is_budget_exhausted(exc) -> bool:
    message = str(exc).casefold()
    if any(m in message for m in _DAILY_QUOTA_MARKERS):     # "tokens per day"
        return True
    if any(m in message for m in _TRANSIENT_RATE_MARKERS):  # "tokens per minute"
        return False
    return any(m in message for m in _BUDGET_ERROR_MARKERS)

billing was deleted from the markers. Deleting it opened a second gap in the other direction — a genuine paywall, one provider returning 402 payment_required, then read as transient — so payment_required was added explicitly. The only thing that caught that was running the four real error messages I had collected through the classifier and printing what each came out as. Four strings, four expected answers, one test.

A fourth axis: the same words, two different clocks

The same provider expresses both of its limits with the same opening phrase:

... rate limit reached ... on tokens per minute (TPM): Limit 12000 ...
... rate limit reached ... on tokens per day   (TPD): Limit 100000, Used 98752 ...

Per-minute reopens inside the run. Per-day does not. So "exhausted" is not only about scope but about whether the window reopens before you finish: a daily quota is exhaustion for this run's purposes even though it is worded identically to the case that clears in seconds. That is why _DAILY_QUOTA_MARKERS is checked first in the function above — it is the narrowest signal available and it outranks wording it shares with the transient case.

Honour the wait the provider states

Independently of classification, there was a second source of wasted attempts. Providers that throttle usually tell you exactly how long to wait:

Please try again in 11.344999999s

My loop ignored that and backed off on its own schedule — 2s, 4s, 8s. Every one of those retries arrived before the window had reopened, was refused, and consumed one of five attempts. The limit would have cleared on its own in eleven seconds; the run instead spent its whole attempt budget arriving early and then escalated to a fallback.

hinted = retry_after_seconds(exc)      # parsed out of the message
wait = hinted if hinted is not None else delay
time.sleep(wait)
if hinted is None:
    delay = min(delay * 2, max_delay)   # exponential only when guessing

Two details worth copying. Add a small margin — half a second — because retrying on the exact boundary is routinely a hair early. And cap what you will honour. A stated wait of an hour is a daily quota in disguise. Above 60 seconds the hint is ignored and the request is classified as exhaustion, rather than blocking the run on it.

Where the header is available rather than a sentence, this is the same idea: Retry-After is a standard response header defined in RFC 9110. Reading it is strictly better than guessing: the server knows when its own window reopens and you do not. It accepts either a number of seconds or an HTTP date, so parse both.

"Should I stop?" needs "and", not "or"

One more shape, which only appears once you have more than one provider to fall back to. The original rule was: if any provider reported exhaustion, abandon the batch. A briefly-throttled primary plus a spend-capped fallback satisfies that, and a run stopped at 4 of 13 jobs while the primary's window was seconds from reopening.

The question the rule is trying to ask is will the next item fail in the same way? — and it will only if every provider failed for a reason that persists. So the condition is "some account is exhausted and nobody merely ran out of patience":

any_transient = any(getattr(e, "transient", False) for _cfg, e in failures)
if budget_failures and not any_transient:
    raise LLMBudgetError(summary)   # nothing will serve; stop the batch
raise LLMError(summary)             # this item failed; the next may not

The first attempt at this rule required all failures to be budget errors. That is wrong in the other direction: a retired model on the primary, plus a capped fallback, would keep going item after item with nothing able to answer. Both mistakes are one word apart. That is the argument for writing the rule as an explicit statement about the list of failures, rather than as flags accumulated inside a loop — and for a test that names both directions.

What I would build on day one now

Three classes, not two. Transient, permanent, exhausted — and decide the third by scope: does this failure predict the next call's failure?

Read the provider's stated wait before applying your own. Cap it, add a margin, and treat an implausibly long one as exhaustion.

Match on specific phrases, in order, narrowest first. Never on a word that could appear in marketing text. tokens per day is a signal; billing is a coincidence.

Keep the real error strings. Four saved messages from live failures were worth more than any reasoning about what providers ought to send, and they are the only reason the paywall case was caught before it ran.

Add a circuit breaker once there is more than one caller. The rules above decide what one batch does. When several jobs share an account, the thing that stops them collectively hammering a struggling provider is a breaker that trips after N consecutive failures and stays open for a cool-down. My news collector has one; the job bot does not, and should.

Log which class you assigned, every time. Every failure above was visible in hindsight only because the retry line recorded how long it waited and whether the figure came from the provider or from the backoff.

One limitation: all of this is calibrated against three providers I actually use, and the marker lists are specific to how they word things. The three classes generalise; the strings do not, and anyone copying this should expect to add their own after the first surprise.

References and further reading

Google's SRE book chapter on handling overload covers the other side of this: why a server sends 429 at all, and why clients retrying aggressively make a struggling service worse rather than better. Its companion chapter on cascading failures is the one to read if your retries are pointed at a service you own.

AWS's timeouts, retries and backoff with jitter is the clearest short explanation of why random jitter belongs in the pause — without it, everything that failed together retries together.

The specifications

  • RFC 6585 §4 — where 429 is defined. Worth reading for how little it says: too many requests, and explicitly not which limit was hit or for how long.
  • RFC 9110 — Retry-After — the header that removes the guesswork, in both its seconds and its date form.
  • RateLimit header fields (IETF draft) — limit, remaining and reset as structured fields. Check whether your provider already sends them before you write a parser for their prose.
  • Stripe — idempotency keys — the other half of retrying safely: how to retry a request that may already have succeeded without doing it twice.

Implementations you can copy instead of writing

  • tenacity — retry policies as decorators, including jitter and per-exception rules, which maps cleanly onto the three classes above.
  • urllib3 Retry — status-aware retries under requests, and it honours Retry-After if you set respect_retry_after_header.
  • Circuit breaker — the pattern for stopping calls entirely after repeated failures, which is what "exhausted" wants once more than one job shares an account.
  • Stripe on rate limiters — written from the server side, and the clearest explanation of why different limits exist and therefore why one status code has to cover all of them.
  • Groq's rate-limit documentation — a concrete example of per-minute and per-day quotas sitting behind the same status, which is the ambiguity the whole post is about.
