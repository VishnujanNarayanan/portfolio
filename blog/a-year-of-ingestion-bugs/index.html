A year of ingestion bugs: what actually broke in 32 market-data pipelines

Vishnujan Narayanan · August 2026

Roughly 30 bugs across a year of scraping Indian market data, sorted by cause. Eight of them produced no error at all, and those were the expensive ones.

Over the last year I fixed about 30 bugs across the 32 scripts that pull Indian market data — prices, corporate announcements, insider filings, news, and a few things I'd rather not admit to scraping. Eight of those bugs produced no error message of any kind. The run exited zero, the CSV got bigger, and the data was wrong. Those eight took far longer to find than the other twenty-two combined, and I think that ratio is the only genuinely interesting thing here.

I'm writing this down mostly because this kind of knowledge evaporates. Six months after you fix something, all that survives is a vague sense that "the insider trades thing was annoying once," which is useless to you and to everyone else. Looking at a year of failures in one place also makes a pattern obvious that isn't obvious one bug at a time.

What broke, by cause

Assigning each bug a single cause is a bit of a lie — the Cloudflare one below belongs in two categories and I put it in the one that cost me more. With that caveat:

The distribution by file is lopsided in a way I didn't expect until I counted. Two scripts account for 16 of the 30: the price downloader (10) and the insider-trades pipeline (6). Both are the ones that maintain long-lived local state across runs. The scripts that just fetch a thing and write a file barely appear.

1. Silently wrong data — 8 bugs

Every one of these ran to completion and reported success. This is the category worth reading about; the other four are here for completeness.

Deduplicating on columns that don't exist

The insider-trades pipeline deduped incoming rows from NSE's insider trading disclosures on a composite key that had been written from memory rather than from the response:

# The key the pipeline actually used. None of these are NSE column
# names, so every row got the same (missing) key and collapsed.
DEDUP_KEYS = ["personName", "acqQty", "securityName"]

# The columns NSE really returns.
DEDUP_KEYS = ["acqName", "secAcq", "symbol", "date"]

Pandas didn't complain in the way I needed it to. The effect was that every distinct trade for a symbol on a given day collapsed into one row — a company that filed four separate trades in a day came out of the pipeline with one. There is no error state here to detect. The pipeline was confidently discarding real filings for as long as that key was wrong, and nothing in the run would ever have told me.

The dedup that added rows

Fixing the key surfaced a second bug underneath it. The dedup was implemented as a merge, and a merge against existing data that already contains duplicate keys doesn't dedup — it does a partial cartesian product and inflates the row count. So for a while the pipeline was dropping rows, and for a while after that it was adding rows that never existed. A set-membership anti-join fixed it, and it doesn't care what's already in the file, which the merge very much did.

If you're doing this with DataFrame.merge, the validate="one_to_one" argument raises on exactly this instead of quietly inflating. I didn't know it existed.

Rows that are all NaN, made permanent

yfinance returns a bar all-or-nothing: if it's throttling you, or if you ask for today's unsettled bar, you get a row with a date and no prices. My loader wrote those rows. Then the resume logic did this:

# Before: any row can become the resume point, including one
# that carries a date and no prices at all.
start = pd.read_csv(path)["Date"].max()

# After: only rows that actually carry a price count.
df = pd.read_csv(path)
start = df[df["Close"].notna()]["Date"].max()

With the first version, a blank row became the high-water mark and every real bar behind it got skipped for good. The gap-repair logic was the thing making the gap permanent. All-NaN frames are now treated as failed fetches rather than data, and existing blank rows get purged at startup.

Filenames that depended on whether I was rate-limited

Per-symbol files were named using the company name looked up at runtime. When the lookup succeeded you got RELIANCE_Reliance Industries.csv; when it was rate-limited and fell back to the bare symbol you got a different filename; when a company got renamed upstream you got a third. Each new filename was an empty file as far as the resume logic was concerned, so it re-downloaded twenty years of history into it. I had symbols sitting in three files with three overlapping partial copies of the same series. Filenames are now stable — reuse any existing SYMBOL_*.csv — plus a consolidation pass at startup that merges duplicates into one canonical file, taking the union of rows and preferring the copy with a valid Close.

A blocked run that looked like a successful one

Trendlyne started returning Cloudflare 405s to plain requests. The supplement step caught the failure, logged it somewhere I wasn't reading, and the overall run reported success with zero rows added — which is indistinguishable from "there was nothing new," which is a completely normal outcome. I switched the fetch to curl_cffi with Chrome impersonation, which gets you a matching TLS fingerprint rather than just a matching user agent. The part of that fix I actually care about is the pass/fail summary printed at the end, so a fully-blocked run can't be mistaken for a quiet one.

The 200-row window

Trendlyne's free tier caps a response at 200 rows. Ask for a 30-day window over a busy period and you get 200 rows and no indication you were truncated. I'd been fetching in wide windows because it was fewer requests; it now chunks one day at a time by default. This is the one I worry about most when scraping. There's no error and no truncation flag anywhere in the response — you get 200 rows and you have to already know that 200 is the cap.

Future-dated rows

Occasionally the source hands back a record dated ahead of today. Left alone it poisons the resume point for the entire symbol — the pipeline now believes it has data through 2027 and stops fetching. Guarded at ingest, same as the blank rows.

2. The source fighting back — 9 bugs

The largest category by count and the least interesting, because every one of these announced itself. 403s from Scrapy until I rotated user agents and slowed the request rate — AutoThrottle does most of that for you and I should have turned it on before writing my own middleware. A Playwright browser that crashed until I ran it headless. Twitter rate-limiting hard enough that the scraper needed seven cycles of three-minute waits on a fresh page, twelve-minute waits mid-scroll, and per-handle re-auth. Cloudflare, twice. Eventually a proxy pool with rotation, because a single IP wasn't going to finish a full crawl.

The useful thing to come out of this category isn't any individual fix but the adaptive worker pool in the price downloader: it starts at five concurrent workers, drops one on any API or rate-limit error, and adds one back after fifteen consecutive clean calls. It means most of these stopped happening rather than each needing to be handled. I wrote about that pattern in building resumable ETL pipelines.

3. Crashes and timeouts — 5 bugs

Unhandled exceptions in thread workers that killed a whole run's worth of progress, and a downloader with no timeout at all that would hang indefinitely on a stalled connection. It now runs with three retries, a ten-second timeout and exponential backoff, and workers return a result object rather than raising into the pool. Nothing clever here — these are the bugs you fix once and stop thinking about.

4. Environment and config — 5 bugs

Hardcoded output directories, three separate times, each one discovered by running the pipeline somewhere other than my machine. A script that broke because I renamed scripts/ to Scripts/ when I moved the project, which is a bug that only exists on case-sensitive filesystems and therefore only appeared on the machine that mattered. Output paths are arguments now.

These are embarrassing rather than interesting, but they're a fifth of the total, which is the kind of thing you only notice by counting.

5. Concurrency — 3 bugs

All three are really one bug I didn't fix properly the first two times. Every worker thread appended its result to a shared combined.csv by reading the file, concatenating, deduping and writing it back:

# Before: every worker reads, merges and rewrites the whole file.
with combined_file_lock:
    combined = pd.read_csv(combined_path)
    combined = pd.concat([combined, new_rows])
    combined = combined.drop_duplicates(["Date", "Symbol"], keep="last")
    combined.to_csv(combined_path, index=False)

# After: workers return frames, one writer commits once.
frames = [f.result().df for f in as_completed(futures)]
(pd.concat(frames)
   .drop_duplicates(["Date", "Symbol"], keep="last")
   .to_csv(combined_path, index=False))

The lock stopped two threads writing at the same instant, which is not the same as making this correct. The whole read-modify-write cycle was still redoing an enormous amount of work, and an interruption mid-write left a truncated file that the next thread would read as the complete dataset and then write back. Three attempts over one day to get this right, which is two more than I'd like to admit for a problem this well-known.

What I'd do differently

The obvious conclusion — write more tests — is one everybody already agrees with and nobody acts on, so here are the two narrower things that would actually have helped.

An empty result and a blocked result are different, and the pipeline has to say which one it got. Three of the eight silent bugs are really the same bug. Cloudflare blocked me, or the window truncated at 200 rows, or the dedup key deleted everything — and in all three cases the output was "zero new rows," which is also what a quiet Tuesday looks like. Anything that can return nothing needs to distinguish "the source had nothing" from "I was prevented from finding out." A pass/fail summary at the end of a run is a crude instrument and it caught two of these.

Don't let the data be its own checkpoint unless you validate it first. Resuming from the newest row in the file is a genuinely good pattern and I still use it — an interrupted run needs no separate state. But any bad row you write becomes the instruction for where to start next time, and two of the eight silent bugs are exactly that. Resume from the newest valid row, where "valid" is defined explicitly per pipeline. If you'd rather not hand-roll the check, pandera lets you declare the schema and column constraints and fail the load instead of writing the row. I'm not using it yet; I probably should be.

The thing I haven't done, and should, is measure how long each of these was live before I caught it. The loud ones are easy: they were fixed within hours of appearing, because they appeared. For the silent ones I genuinely don't know, and that's the point — nothing in my setup records when a bug started, only when I got around to fixing it.

Caveats on the count

"About 30" is doing some work in that sentence, and I'd rather state the ways it's soft than have you assume I didn't notice.

  • Small bugs I fixed while doing something else don't appear at all, so 30 is an undercount. My guess is the real number is meaningfully higher, but I have no way to estimate by how much.
  • The three concurrency entries are one bug I got wrong twice, and two of the price-downloader entries are similar. Counting those as one each moves the totals around by a few.
  • Classification is my own judgment after the fact, which biases it toward the story I already had in my head when I started counting. The silent-versus-loud split is stark enough that I don't think this changes the conclusion, but it would easily move a category boundary by two or three.
  • Most importantly, this counts bugs I found. The whole argument here is that a class of bug exists that produces no signal, which means the honest position is that I have no idea how many are in there right now.

Which is roughly where I've landed: the loud failures are a solved problem and mostly handle themselves now, and the silent ones I catch by luck. Closing that gap probably means re-fetching data I already have and diffing it against itself on a schedule, which is the next thing I want to build, and which I suspect will find things I won't enjoy. The stack this came out of is described on the market-data pipeline page, and the dedup problems in more detail in scraping NSE insider filings.

Elsewhere

Ding Yuan et al., Simple Testing Can Prevent Most Critical Failures (OSDI '14), looked at catastrophic failures in Cassandra, HBase, HDFS, MapReduce and Redis and found the majority came from error-handling code that was wrong or empty rather than from the original error. Mine is smaller and much less rigorous, but the shape is the same: the failure that hurts isn't the one that throws.

Jepsen's analyses are the best demonstration I know that a system will happily tell you everything is fine while losing your writes, and that the only way to know otherwise is to go looking on purpose. Different scale, same problem as the dedup key.
