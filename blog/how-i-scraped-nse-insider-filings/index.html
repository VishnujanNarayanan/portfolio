How I scraped 20 years of NSE insider filings

Data engineering10 min readPublished August 2026

India's National Stock Exchange publishes insider-trade disclosures through its PIT (Prohibition of Insider Trading) endpoint, and it will hand you a few weeks of data quite happily. Ask it for twenty years and it does not refuse — it times out, or truncates, or returns a partial page that looks exactly like a complete one. Backfilling two decades into a dataset that reruns safely took three things: the right window size, a deduplication key that survives two sources, and a second source entirely.

Twenty years is not one download

The naive request fails in several ways at once, and only one of them is loud. Wide ranges time out. Slightly less wide ranges return without error and without all the rows. So the first decision is to stop treating this as one job:

DEFAULT_CHUNK_DAYS = 180   # max span fetched per API request when looping a wide range

def fetch_range(session, from_date, to_date, chunk_days, retries=3):
    """Fetch a (possibly wide) date range by splitting it into chunk_days windows."""
    start = from_date
    while start <= to_date:
        end = min(start + timedelta(days=chunk_days - 1), to_date)
        ...
        start = end + timedelta(days=1)

180 days is the number I settled on: small enough that the endpoint reliably returns everything in the window, large enough that twenty years is roughly forty requests rather than thousands. It is not a documented limit — I found it by walking the window size up until results started going missing, which is the only way to find an undocumented cap.

The run modes fall out of the same structure. First run backfills twenty years. Every run after that re-pulls from the newest record already stored, minus a buffer, through today. The buffer is not superstition: filings arrive late, so a window that starts exactly where you stopped will permanently miss anything that was filed for a date you already passed.

The dedup key that deleted data

Overlapping windows are the whole point of the buffer, so deduplication is load-bearing. For months mine ran on this:

# Written from memory instead of from the response. None of these are
# real NSE column names.
DEDUP_KEYS = ['personName', 'acqQty', 'securityName']

# What the endpoint actually returns.
DEDUP_KEYS = ['symbol', 'intimDt', 'acqName', 'secAcq']

Because none of the first three columns existed, every row produced the same missing key, and every distinct filing for a symbol on a given day collapsed into a single row. A company that disclosed four separate transactions in a day was stored as one. Nothing raised, nothing logged, and the row count looked plausible because it was never compared to anything.

Fixing the key exposed a second bug beneath it. The dedup was a merge, and a merge against existing data that already contains duplicate keys inflates rather than collapses — a partial cartesian product. So the pipeline went from dropping filings to inventing them. A set-membership anti-join has neither failure mode, and does not care what is already in the file:

def deduplicate(new_df, existing_df):
    new_keys = _composite_key(new_df, DEDUP_KEYS)
    existing_keys = set(_composite_key(existing_df, DEDUP_KEYS))
    return new_df[(~new_keys.isin(existing_keys)).values]

If you are reaching for DataFrame.merge here, validate="one_to_one" raises on exactly the inflation case instead of silently doing it.

Normalising keys so two sources agree

A composite key only works if the same record produces the same key every time, and it does not. The same quantity arrives as 629221 from one place and 629221.0 from another. The same date is 15-Jan-2026 here and 2026-01-15 there. Unnormalised, those are distinct keys and the row is stored twice:

for k in dedup_keys:
    if k == 'intimDt':
        col = pd.to_datetime(df[k], errors='coerce').dt.strftime('%Y-%m-%d')
    else:
        # '100', 100 and 100.0 all collapse to one key;
        # non-numeric values (names) fall back to their string form.
        numeric = pd.to_numeric(df[k], errors='coerce').astype('float64')
        col = numeric.where(numeric.notna(), df[k]).astype(str)
    parts.append(col.fillna('').astype(str))
return parts[0].str.cat(parts[1:], sep='|')

This is the piece that makes the next section possible. Without it, merging a second source produces a dataset that is duplicated everywhere the two overlap, which is worse than having one source.

NSE lags itself by a month or more

The bigger problem is not collection, it is timeliness. Filings take roughly 30 to 60 days to appear in NSE's indexed history. For a backfill that is irrelevant; for anything current it means the most recent two months of your dataset are systematically incomplete, and nothing about the response tells you so.

So the pipeline supplements the last 60 days from a second source, mapped onto NSE's 32-column schema and deduplicated against it with the normalised key above. That is only sound because the key normalisation makes cross-source matching reliable — otherwise you are stacking two partially-overlapping datasets and calling it coverage.

The second source fought back in two specific ways worth knowing about:

  • Cloudflare 405s to plain requests. Rotating the user agent does nothing here, because the block keys on the TLS fingerprint rather than the header. curl_cffi with Chrome impersonation gets a matching fingerprint. Worse than the block itself: the run reported success with zero new rows, which is indistinguishable from a quiet day. It now prints an explicit pass/fail summary so a fully-blocked run cannot be mistaken for an empty one.
  • A 200-row cap per window on the free tier. Wider windows silently return the first 200 records with no truncation flag anywhere in the response. The supplement fetches one day at a time by default for this reason. You cannot detect this without knowing the cap exists.

A single IP will not finish a full historical crawl of that source either, so the crawl runs through a rotating proxy pool. Free proxies are fine for testing rotation and not for a real run.

What I would change

Verify counts against something external. Every silent failure above shares one property: the output was plausible and unchecked. A filing count for a handful of known symbols, compared against the exchange's own published figures, would have caught the dedup-key bug immediately instead of eventually.

Treat "zero new rows" as suspicious by default. It is the correct answer often enough to be unremarkable and wrong often enough to be dangerous. Anything that can legitimately return nothing needs to distinguish an empty source from a refused request.

Decide what a restatement means before it happens. If a filing is corrected upstream, my dedup key sees a record it already holds and drops the correction. That was never a decision, it is a consequence of using set membership, and for a compliance-adjacent dataset it is the gap that bothers me most.

The full accounting of what has broken across these pipelines is in a year of ingestion bugs, the rerun guards are in reruns that converge, and the wider stack is on the market-data platform page.

Elsewhere

SEBI's Prohibition of Insider Trading Regulations, 2015 (the original 2015 gazette notification; it has been amended since) define what has to be disclosed and within what deadline, which is what sets the shape of the data and the reporting lag you have to design around.

NSE's insider trading disclosures page is the human-facing view of the same records the endpoint serves — useful for spot-checking a symbol when you suspect your own pipeline.
