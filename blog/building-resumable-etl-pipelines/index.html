Making pipeline reruns converge instead of drift

Data engineering8 min readPublished August 2026

The rule I hold every ingestion pipeline to is that running it again must move the dataset toward correctness. Fill a gap, fix a bad row, leave everything else alone. It should not be possible for a second run to make the data worse than one run.

Across 28 ingestion pipelines that pull Indian market data, I have broken that rule in four distinct ways, and each break produced a dataset that looked fine. This is what the guards are, what each one was added in response to, and the one case where I still cannot promise convergence.

The data is the checkpoint — so validate it before trusting it

Every pipeline resumes by asking the data where it stopped, rather than keeping a separate checkpoint file. Interrupted run, killed process, machine reboot: restart it and each symbol picks up from its own last row. No state to corrupt, no lockfile to go stale.

That property is also how I destroyed several months of history. The price source returns a bar all-or-nothing, so a throttled request or a request for today's unsettled bar comes back as a row with a date and no prices. The loader wrote them, and then:

# Resume point = newest date in the file, valid or not.
start = pd.read_csv(path)["Date"].max()

A blank row dated today becomes the high-water mark, and every real bar behind it is never fetched again. The gap-repair mechanism was what made the gap permanent. The fix is one predicate:

# Resume only from rows that actually carry a price.
df = pd.read_csv(path)
start = df[df["Close"].notna()]["Date"].max()

Plus the two corollaries: a download frame that is entirely NaN is treated as a failed fetch rather than data, and a startup pass purges blank rows already on disk so old damage heals instead of persisting. A row dated in the future gets the same treatment — left alone it convinces the pipeline it has data through 2027 and stops fetching entirely.

The general form: if the data is your checkpoint, then every write is also a write to your control flow. Validate before writing, or you are appending instructions as well as rows.

Identity has to be stable across runs

Per-symbol files were named with the company name looked up at runtime. That lookup is rate-limited, so it returns the real name when the source is healthy and the bare symbol when it is not — and a different name again when a company gets renamed upstream. Three names, three filenames, three files that each looked to the resume logic like a symbol with no history. Each run happily re-downloaded twenty years into a fresh file.

Two guards. Filenames are resolved by reusing any existing SYMBOL_*.csv rather than by regenerating the name, so identity is decided once and then remembered. And a consolidation pass at startup merges any duplicates that already exist into one canonical file, taking the union of rows and preferring the copy with a valid Close where they disagree.

The lesson generalises past filenames: anything that derives an identifier from a network call will eventually derive a different one. If that identifier decides where data goes, a bad minute at the source becomes a permanent fork in your dataset.

Dedup with an anti-join, not a merge

Overlapping windows are unavoidable — reruns deliberately re-pull a buffer of recent history so late-arriving records get picked up. That makes deduplication load-bearing rather than defensive.

I originally implemented it as a merge. A merge against existing data that already contains duplicate keys does not deduplicate; it does a partial cartesian product and multiplies rows. Set membership does not have that failure mode:

def deduplicate(new_df, existing_df):
    new_keys = _composite_key(new_df, DEDUP_KEYS)
    existing_keys = set(_composite_key(existing_df, DEDUP_KEYS))
    # Set-membership anti-join — immune to duplicate keys in existing_df
    # (a merge cartesian-inflates when the right side has repeats).
    return new_df[(~new_keys.isin(existing_keys)).values]

The composite key itself needs normalising, because the same record does not arrive identically twice. A quantity comes back as 629221 from one endpoint and 629221.0 from another; a date is 15-Jan-2026 in one and 2026-01-15 in the other. Unnormalised, those are different keys and you store the row twice:

for k in dedup_keys:
    if k == 'intimDt':
        col = pd.to_datetime(df[k], errors='coerce').dt.strftime('%Y-%m-%d')
    else:
        # '100', 100 and 100.0 collapse to one key; names fall back to string.
        numeric = pd.to_numeric(df[k], errors='coerce').astype('float64')
        col = numeric.where(numeric.notna(), df[k]).astype(str)
    parts.append(col.fillna('').astype(str))

One warning from experience: the key must be built from column names that actually exist in the response. I once deduplicated on three fields that were not real column names, which produced an identical empty key for every row and collapsed every filing for a symbol on a given day into one. Nothing raised. If you are using DataFrame.merge for this, validate="one_to_one" turns the silent inflation into an exception.

Pace against the source, don't fight it

Convergence assumes the source keeps answering. A pipeline that hammers a rate limit gets partial responses, and partial responses are how bad rows get written in the first place — so backoff is a data-quality control, not just politeness.

The price downloader runs a thread pool whose size moves on its own: five workers, drop one on any API or rate-limit error, add one back after fifteen consecutive clean calls. Individual requests get three retries with exponential backoff and a ten-second timeout. It speeds up when the source is healthy and slows down the moment it pushes back, with no manual tuning and no fixed sleep that is either too slow or too aggressive depending on the day.

Where I can't promise convergence

All of the above makes reruns converge against my errors. None of it helps when the source itself changes an old value.

If a record is restated upstream — a corrected filing, an adjusted price after a corporate action — my dedup key sees a row it already has and drops the correction on the floor. Convergence and immutability are in direct conflict here, and I chose immutability without really deciding to. For prices this is mostly handled because corporate-action adjustment gets recomputed, but for filings it is a real gap.

I also cannot currently tell the difference between "the source had nothing new" and "the source refused to answer," which is the failure mode that has cost me the most across these pipelines. I wrote up the full accounting of that in a year of ingestion bugs. The next thing I want to build is a scheduled re-fetch that diffs old data against itself, which is the only way I can see to detect both problems.

Elsewhere

Jepsen is the reference point for the general shape of this problem: systems that report success while silently losing or duplicating writes, findable only by checking on purpose rather than waiting for an error.

pandera lets you declare the schema and column constraints and fail a load rather than writing an invalid row — the declarative version of the hand-rolled validity checks above. I am not using it yet; I probably should be.

The pipelines described here are part of the market-data platform, and the chunking and reconciliation side of it is in scraping NSE insider filings.
