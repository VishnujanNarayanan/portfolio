Why your scraper gets blocked, and what actually fixes it

Vishnujan Narayanan · July 2026

Rotating user agents fixes almost nothing. A walk down the stack — IP, TLS fingerprint, browser signals, behaviour — with what each block looks like and what stopped it.

A stock-data site I collect from started answering my script with 405 Method Not Allowed. Nothing had changed on my side. The advice you find first — rotate your user agent, add some headers — could not have worked, because the site was not reading my headers. It was looking at the shape of the encrypted connection itself, which is decided before a single header is sent.

Blocking is not one thing, and that is the whole difficulty. There are four separate layers at which a site can decide you are not welcome, they produce similar-looking failures, and a fix aimed at the wrong layer does nothing at all. This is each layer, what it looks like from the outside, and what actually stopped it in my own collection scripts.

First, the thing that makes all of this hard to debug

When that 405 started, my run reported success. It fetched, it caught the error, it logged it somewhere nobody was reading, and it finished with zero new rows — which is exactly what a quiet day looks like. The data simply stopped growing.

Anything that can legitimately return nothing has to be able to tell the source had nothing apart from I was prevented from finding out. Before any of the fixes below, the change that mattered was an explicit pass/fail count printed at the end of every run, so a block shows up as a block. Three of the bugs in my year of ingestion bugs were the same shape.

Layer 1 — what you say: headers

Every HTTP request carries a set of labels: which browser you claim to be, what you will accept back, which page you came from. This is the layer everyone starts with, and it is the least likely to be your problem — but getting it wrong will block you on sites that block nothing else. ScrapeOps keeps a practical guide to header sets that is more specific than most, if you want a checklist for this layer.

The National Stock Exchange's data endpoints are the clearest example I have. They will not answer unless the request looks like it came from the page that normally calls them:

HEADERS = {
    "User-Agent": "Mozilla/5.0",
    "Accept": "application/json",
    "Referer": "https://www.nseindia.com/companies-listing/corporate-filings-insider-trading",
    "Accept-Language": "en-US,en;q=0.9",
}

The Referer is the load-bearing line: it says which page sent you. Many sites also require that you visited the ordinary page first, because that visit is what issues the cookie the data endpoint checks. Nothing here is clever, and rotating through a list of fake user agents adds nothing on top — a site that checks headers checks whether they are coherent, not whether they are varied.

Layer 2 — how you connect: the TLS fingerprint

This is the layer that produced the 405, and the one most people have not heard of.

Before any HTTP request happens, your program and the server negotiate an encrypted connection. In that opening message your side lists which encryption methods it supports, in a particular order, with particular extensions. Python's networking library makes that list differently from Chrome. The pattern is stable enough to be summarised as a fingerprint — the common form is called JA3, now largely superseded by JA4 — and a bot-mitigation service can compare it against what a real Chrome produces before it has read one byte of your request. You can see your own in about two seconds: fetch tls.browserleaks.com/json from your script and then from your browser, and compare the fingerprint fields.

So a request claiming to be Chrome, whose handshake is Python's, is caught by a check that never looks at the claim. You cannot fix this with headers, and you cannot fix it by trying harder in the same library. What fixes it is making the handshake itself match:

# curl_cffi impersonates a real browser's TLS/JA3 fingerprint, which is what
# gets past Trendlyne's Cloudflare bot mitigation (plain `requests` gets 405'd).
from curl_cffi import requests as cffi_requests

resp = cffi_requests.get(url, headers=HEADERS, impersonate="chrome131")

curl_cffi is a drop-in replacement for Python's requests that speaks through a TLS stack configured to match a named browser version. One import and one argument. The rest of the script was unchanged, and the endpoint started answering again.

How to tell this is your layer: the same URL works in your browser, often works from curl on the command line, and fails from your script with a status that has nothing to do with the request being malformed — 403, 405, or a challenge page. Getting a challenge page while a real browser on the same machine and network sails through is the tell. If you are not in Python, tls-client is the equivalent for Go, and the same technique underlies most commercial "unblocker" products.

Layer 3 — where you connect from: the address

Once your handshake looks right and your headers look right, the next thing a site has is your IP address, and it knows two things about it: whether it belongs to a home connection or a data centre, and how it has behaved recently.

Both of my clearest blocks were at this layer. The insider-filings supplement, after enough requests, started getting Cloudflare's "confirm you are human" wall — served as ordinary-looking HTML with a 403, 405, 429 or 503 attached. Detecting it needs both signals, because the status alone is ambiguous and the page alone is just text:

BLOCK_STATUS = {403, 405, 429, 503}
CHALLENGE_MARKERS = ("cf-chl", "challenge-platform", "/cdn-cgi/challenge")

def looks_blocked(status_code, text=""):
    """True if a response is a Cloudflare block/challenge rather than real content."""
    return status_code in BLOCK_STATUS or any(m in text for m in CHALLENGE_MARKERS)

The response to that is rotation: a pool of proxy addresses, a fixed number of requests taken through each before moving to the next, and a fresh batch pulled and tested when the pool wears out. Mine leases 10 requests per address, pauses 30 to 90 seconds between batches of 20, and validates every candidate address against the real site before trusting it — free proxy lists are mostly dead entries, so the validation pass is not optional.

Two honest caveats, because this is the layer where advice gets irresponsible. First, free proxies are unreliable, frequently slower than not scraping at all, and you have no idea who operates them, which makes them unfit for anything carrying credentials. Second, rotation treats a symptom. If a site blocks your address after 200 requests, the reason is usually the rate rather than the identity, and pacing the run is the fix that keeps working when rotation stops.

The other case is more interesting because rotation was not available. My book-catalogue app runs on a hosting provider and fetches pages from a retailer on demand. The retailer blocks data-centre addresses, which is every address the app has. Rotating within a data centre does not help when the data centre is the thing being scored. The change was to move the fetch to the one address the site had no reason to distrust — the visitor's own browser, which loads the page and hands the result back to the API. That path is open source in product-explorer, and the project page covers why the app fetches on demand at all. The commit message is the summary: scrape from the visitor's browser, because ours is the address being blocked.

Layer 4 — whether you look like a person

Running a real browser gets you past the first two layers automatically, and introduces a fourth: automated browsers announce themselves. The most famous signal is a property the browser sets when it is being driven by a program, which is one line of JavaScript to read:

Object.defineProperty(navigator, 'webdriver', {get: () => undefined});
Object.defineProperty(navigator, 'languages', {get: () => ['en-US', 'en']});
Object.defineProperty(navigator, 'hardwareConcurrency', {get: () => 8});

There are dozens more — screen size, available fonts, how the browser renders a test image, whether a headless build reports the same graphics driver as a real one. Libraries exist to patch the known set; I use playwright-stealth where I need it, and undetected-chromedriver is the Selenium equivalent. Treat that as raising the bar rather than clearing it: this is an arms race between people who publish patches and people who publish new checks, and the checks are updated more often.

The other half of this layer is behaviour, and it is the half that actually decides. A real session has irregular gaps, does not request 400 pages in perfect 1.0-second intervals, and does not run at 03:00 for exactly the same duration every night. Jittered pauses and batch breaks cost almost nothing and remove the most obvious pattern you present.

Where I have needed the strongest measures — a couple of sources that check hard — the answer was to stop hiding: run the browser visibly rather than headless, log in once by hand, and save the session to a file so later runs start already authenticated. That is described in Playwright vs Selenium.

The block that is not a block

Two more failures look like blocking and are not.

Rate limiting. A 429 usually means slow down, and it clears on its own. It is not a verdict on you, and responding to it by rotating addresses converts a two-minute pause into a real block. It also has more than one meaning, which is its own post: what a 429 really means.

A cap you were never told about. The same supplement source silently truncates any response at 200 rows for non-subscribers. No error, no flag, no indication that anything was withheld — a wide date window simply returns fewer records than it contains. The fix was to request one day at a time so no window can reach the cap. Nothing in the response would ever have told me; it was findable only by pulling a range twice with different window sizes and noticing the totals disagreed.

The order I would work through it

Cheapest first, because each step rules out a layer:

1. Make the failure visible. Print how many requests succeeded and how many were refused. Everything below is guesswork until a block is distinguishable from a quiet day.

2. Check whether you need the page at all. Open the browser's network tab and look for the endpoint the page itself calls. A JSON endpoint with the right Referer is less work to keep alive than a browser, and a smaller thing to be blocked for.

3. Fix the headers, once. Real user agent, correct Referer, visit the ordinary page first so you hold the cookie.

4. Match the handshake with curl_cffi or equivalent, if you get challenge pages that a browser on the same machine does not.

5. Slow down before you rotate. Pacing fixes rate-based blocks permanently; rotation fixes them until the new address is scored too. Scrapy's AutoThrottle and Crawlee both do this adaptively, which beats any fixed delay you will pick by hand.

6. Use a real browser only when the content genuinely does not exist without JavaScript — and expect layer 4 once you do.

The part that is not technical

All of the above is about whether a request succeeds, which is a different question from whether it should be made. What I hold to: public data only, never anything behind a paywall or another person's login, honour robots.txt and the terms where they speak to this, keep the request rate low enough that nobody would notice the load, and identify honestly where a site offers a way to. Every rate limit and pause described here also exists for that reason, not only to stay unblocked. If a site offers an API or a bulk download, that is the correct route even when it costs money, and it will outlive any of these techniques.

References and further reading

Cloudflare's own bot score documentation is the clearest description of these layers from the defending side: it names the signals, and it says plainly that the score is a learned combination of them rather than a rule you can satisfy.

Salesforce's JA3 repository explains how a handshake becomes a fingerprint in about a page, and JA4 is the current successor. Read one of them if layer 2 was new to you — it is the piece most scraping guides never mention.

Tools, by layer

  • curl_cffi (layer 2) — requests-compatible calls with a browser's TLS handshake. One import and an impersonate= argument.
  • browserleaks TLS probe (layer 2) — fetch it from your code and from your browser; if the fingerprints differ, that is your block.
  • tls-client (layer 2) — the same capability for Go.
  • Scrapy AutoThrottle and Crawlee (layer 3) — adaptive pacing, retries and proxy rotation, instead of hand-tuned delays.
  • playwright-stealth and undetected-chromedriver (layer 4) — the published patches for known automation signals. Both raise the bar rather than clearing it.
  • curl on HTTP cookies (layer 1) — worth reading when a site only answers after you have loaded an ordinary page first, which is a cookie problem wearing a blocking costume.

Rules, standards, and the legal side

  • RFC 9309 — the Robots Exclusion Protocol, standardised only in 2022, which is more recent than most people assume. Python's robotparser reads it in three lines.
  • MDN on 429 — being throttled versus being blocked, which decides whether to wait or to change something.
  • EFF on hiQ v. LinkedIn — the US appeals ruling that scraping publicly available data is not "unauthorised access" under the computer-crime statute. Context, not legal advice: it says nothing about contract terms, copyright, or other jurisdictions.
